# Эксплуатационные проверки MVP

## Readiness и HTTP-логи

GET /api/health — liveness процесса. GET /api/ready — проверка подключения и исходной структуры БД: 200 ready либо503 unavailable без внутренних сообщений. Это не проверка всех бизнес-данных и не гарантия доступности интеграций. Docker healthcheck использует ready; миграции выполняются при старте. Внешний мониторинг и автоматическое переключение не подключены.

Приложение пишет JSON-события portfolio.http: request_id, метод, шаблон маршрута, HTTP-статус, длительность и тип необработанной ошибки. Тело, query string, исходный URL, cookies, email, IP и входящий X-Request-ID не записываются. Неизвестный маршрут обозначается unmatched. request_id генерируется сервером и возвращается заголовком. Необработанный HTTP-сбой даёт500 с общим текстом, без SQL-параметров и traceback в ответе/этом логе.

Запускайте uvicorn с --no-access-log, чтобы стандартный access logger не печатал URL с query. Docker и browser CI настроены так. Это ограниченная HTTP-инструментация, не аудит логирования всех библиотек, не система метрик/алертов и не полный централизованный мониторинг. При разборе ошибки используйте request_id и воспроизводимый локальный сценарий с тестовыми данными.

## SQLite: новый файл для backup и restore

Создайте локальную папку backups, выберите новый уникальный путь. Выполняйте из корня репозитория в его Python-окружении:

    python -m app.sqlite_backup backup ledger.sqlite backups/snapshot.sqlite
    python -m app.sqlite_backup restore backups/snapshot.sqlite restored-review.sqlite

Операции используют sqlite3.Connection.backup, поэтому копируют согласованный снимок, включая committed WAL-данные. Проверяются integrity_check и foreign_key_check. Существующий целевой файл не перезаписывается. Повреждённый источник отклоняется; создаваемый при сбое новый файл удаляется. Restore всегда создаёт отдельный файл и сам не переключает приложение.

Для проверки остановите тестовый экземпляр, настройте DATABASE_PATH (Deskline) либо DATABASE_URL (Commerce/Ledger) на restored-review.sqlite, запустите изолированный экземпляр без пользовательского трафика и проверьте вход, счётчики и ключевой пользовательский сценарий. Сравните данные с моментом снимка. Продуктивный процесс и исходную базу до проверки не переключайте. Сохраните исходный файл для отката; не копируйте активный SQLite-файл обычным копированием без учёта WAL.

Тесты доказывают перенос committed-строки при открытой uncommitted-транзакции, сохранение внешнего ключа, отказ перезаписи и отказ повреждённому файлу. Это не обещание нулевой потери данных: записи после момента backup в снимок не входят.

## PostgreSQL: custom dump и пустая база

На машине с Python-окружением проекта установите клиентские pg_dump/pg_restore совместимой версии (для этого проекта PostgreSQL17). Настройте PGHOST, PGPORT, PGUSER и явный PGDATABASE. Пароль задайте только локально через .pgpass или окружение; не помещайте его в команду, URL, Git, чат и общие логи. PGDATABASE принимает простое имя длиной до63 символов, не connection URL.

    python -m app.pg_backup backup backups/database.dump

Создайте отдельную пустую базу restored_review с нужными правами, например локальным createdb. Измените PGDATABASE на restored_review и выполните:

    python -m app.pg_backup restore backups/database.dump

Restore принимает только пустую целевую базу, не использует --clean и не удаляет чужие объекты. Восстановление идёт одной транзакцией с exit-on-error; stderr не публикуется, ошибка сообщается общим текстом. Все процессы записи в целевую базу должны быть остановлены: проверка пустоты сама по себе не блокирует конкурирующее создание объектов. Используйте только собственный доверенный dump, поскольку восстановление может выполнять код из источника.

После восстановления проверьте версию Alembic, число пользователей/операций/заказов и связи, затем запустите приложение в отдельном окружении, проверьте вход и основной сценарий. Только после проверки и остановки записи на исходном экземпляре меняйте DATABASE_URL. Возврат конфигурации к исходной базе — отдельный план отката; новые записи после переключения требуют согласования, автоматического объединения нет.

В Linux CI PG_USE_DOCKER=1 использует официальный postgres:17-alpine с сетью host и клиентом той же версии; этот режим требует Docker и не предназначен для Windows. Тест создаёт две уникальные временные базы, переносит BigInteger/внешний ключ и проверяет отказ restore в непустую базу. В PostgreSQL-сервисе CI нужны права CREATEDB; прикладной runtime не обязан иметь такие права. Кластерные роли, tablespaces, PITR/WAL-архивирование и offsite-восстановление этим тестом не покрываются.

[pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html), [настройка .pgpass](https://www.postgresql.org/docs/17/libpq-pgpass.html).

## Границы проверки

Backup содержит личные данные, хеши паролей и сессии: ограничьте доступ к файлам. backups/, *.dump, *.backup и SQLite-файлы исключены из Git. Не включайте их в артефакты CI. Здесь нет шифрования, ротации, расписания backup, внешнего хранилища и измеренных RPO/RTO. Восстановление нужно регулярно репетировать в отдельном окружении; эти MVP не объявляются production-сервисами.

[Python SQLite backup API](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup).
